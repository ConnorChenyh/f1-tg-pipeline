## 0. 执行摘要

这是一个**工程质量明显高于同类个人项目平均水平的项目**：架构文档真实、确定性门控思路正确、测试有真实断言、失败模式考虑过（Telegram 补偿队列、文章抓取降级、采集器隔离）。

但存在 **3 个必须尽快处理的正确性缺陷**，其中 1 个会直接导致当天新闻发不出去，1 个会静默篡改生产记忆。

| 严重度 | 问题 | 影响 |
|---|---|---|
| **P0** | `--mock` 污染生产状态 | 手动跑一次 mock，真实话题被压制 7 天 |
| **P0** | LLM 输出契约未校验 | 模型返回 `{}`/缺字段 → `KeyError` → 无条件重试 1 次后整日掉线 |
| **P1** | 质量门禁 fail-closed | 正则误杀 → 抛异常 → 当天草稿不落盘、不发通知、直接 exit 1 |
| **P1** | 图片静默截断正文 | 违反"每条必须单图完整显示"的核心约束，且无告警 |
| **P1** | 无成本/延迟治理 | 不知道每次运行花多少钱、慢在哪 |

综合加权得分：**56 / 100**（3 分制均值约 2.8/5）——「良好但不设防」。

最高杠杆的改进（成本都很低）：
1. 给 `generator/` 加**提示词版本号 + 冻结黄金集**；
2. 给 `publisher/` 加**重复投递测试**（重跑会不会重复发）；
3. `--mock` 状态隔离（P0-1，30 分钟工作量）。

来自 GitHub 同类项目调研的额外结论（详见第 7 节）：

- **架构方向是对的**：Telegram 转人工发布是当前唯一合规路径。小红书 2026-07-17 公告明确禁止 AI 自动发布，并处置了 42 万个账号；生态 issue 里有"仅读取一次帖子就被警告"的实证。**不要接自动发布。**
- **最值得抄的一项**：用 HTML/CSS + Playwright 渲染卡片（[Pitwall-Media](https://github.com/SOUMILCHANDRA/Pitwall-Media)、[guizang-social-card-skill](https://github.com/op7418/guizang-social-card-skill)），因为本项目现在**同时维护 Pillow 和 HTML 两套排版**，且 Pillow 那套正有 P1-2 的截断缺陷。
- **最严重的生态级差距**：本项目**纯文本驱动、从不查官方 F1 数据**，所以积分榜/赛果/罚单这类数字在构造上不可验证。建议用 Ergast 兼容的 [jolpica-f1](https://github.com/jolpica/jolpica-f1) JSON API 替掉 `standings.py` 里只认四大车队的 HTML 正则。

## 3. 发现清单

### 3.1 P0 — 必须修

#### P0-1 `--mock` 会污染生产状态（已复现）

`run.py` 在 mock 分支里完全绕过了证据门控与历史过滤：

```python
# run.py:331-334
if args.mock:
    topics = enrich_topics_with_evidence(mock_topics(shortlisted), shortlisted)
    topics = enrich_evidence_with_articles(topics, config)
    client = None      # ← 没有 filter_topics_by_evidence_quality / story_db / topic_history
```

但收尾阶段**无条件**写记忆：

```python
# run.py:441-443
if not args.telegram_dry_run:
    append_topic_history(digest_topics, ROOT, config, run_context.generated_at)
    record_published_topics(digest_topics, ROOT, config, run_context.generated_at)
```

实测（本次评审执行 `run.py --mock --hours 24`）：

```
topic_history entries: 3   ← mock 话题被记为"已发布"
published_topics: 3        ← SQLite 同样写入
season_context_state.json  ← 也被创建/推进
```

后果：接下来 7 天内真实出现同样话题时会被 `shared_url` / `text_similarity` / `story_db` 静默丢弃。`--dry-run` 提前 return 所以安全，只有 `--mock` 有这个洞。

**修法**（三选一，推荐第 1 个）：
1. mock 分支直接复用真实分支的门控调用链，只是 topics 来源换成 `mock_topics`；
2. `--mock` 时把 `topic_history.path` / `story_db.path` / 季节快照路径重定向到临时目录；
3. mock / dry-run 一律不写记忆（把写记忆放进 `if not args.mock and not args.dry_run`）。

#### P0-2 LLM 输出契约未校验

`DeepSeekClient._extract_json` 只要有合法 JSON 就返回，**不校验形状**；`chat_json` 的 `try` 覆盖了 `_extract_json`，于是形状错误也被当成"调用失败"重试：

```python
# generator/deepseek_client.py:59-73
for attempt in range(attempts):
    try:
        response = self.client.chat.completions.create(...)
        return self._extract_json(content)
    except Exception as exc:
        last_error = exc          # ← 校验失败也走这里
        logger.warning(...)
raise RuntimeError(...)
```

接着：

- `analyzer/topics.py:98` → `int(t.get("heat_score", 0))`：模型给 `"85分"` 直接 `ValueError`，且**不在重试范围内**（异常发生在 `extract_topics` 之后），整个 run 挂掉；
- `generator/digest_writer.py:104` → 只检查 `isinstance(draft, dict)`，模型返回 `{}` 时通过，随后 `validate_digest` 报 `too_few_items` error → 抛异常；
- `response_format={"type": "json_object"}` **完全没用**（DeepSeek 支持），却用正则 `JSON_BLOCK_RE` 去猜 JSON。

`max_retries: 1` 意味着只有 2 次机会，反序列化/形状错误不可重试（重试同一 prompt 通常得到同样错误）。

**修法**：
- 给 `chat_json` 加 `required_keys` / JSON Schema 参数，形状不符时**带着错误信息重新提问**（repair 提示），而不是原样重发；
- 打开 `response_format` 让 JSON 合法性由服务端保证；
- `heat_score` 解析加 `try/except` + 默认值。

### 3.2 P1 — 应该修

#### P1-1 质量门禁 fail-closed，失败即"静默掉线"

`generator/digest_writer.py:157-159` 只要有一个 `severity="error"` 就抛异常；`run.py:459-461` 捕获后 `return 1`——**草稿不落盘、不通知、不落 pending 队列**。而"error"级规则是若干**写死的汉语正则**：

```python
# generator/quality_guard.py:21-35
EVENT_CONFLATION_PATTERNS = [("event_conflation_balcony", re.compile(r"驾驶[^。！？，；、\n]{0,35}(?:登上|走上|开上|冲上)...阳台"), ...)]
RACE_LOCATION_PATTERNS  = [("impossible_bahrain_malaysia_race_location", re.compile(r"(?:于|在)马来西亚[^。！？，；、\n]{0,12}举行的巴林大奖赛"), ...)]
```

这明显是对历史事故的逐条过拟合（`tests/test_quality_pipeline.py` 里有对应的 7 个用例）。它无法覆盖新事故，却可能误杀正确表述。

**建议**：门禁失败改为**降级但产出** —— 把草稿标 `needs_review` 存盘并推 Telegram 告警，由人来判断，而不是让当天颗粒无收。真正的静默失败（无产出、无通知）比一条措辞有争议的新闻危险得多。

#### P1-2 图片静默截断正文

```python
# generator/images.py:160-167
chosen_font = _load_font(22)
chosen_lines = _wrap_text(draw, text, chosen_font, text_width)
while chosen_lines and _measure_lines_height(...) > body_height:
    chosen_lines.pop()                                    # ← 直接丢字
if chosen_lines:
    chosen_lines[-1] = chosen_lines[-1].rstrip("。；，,") + "…"
```

`item_max_chars: 500` 与单图容量不匹配时会**丢掉正文尾部且只记一条 warn**（`too_long_item` 是 `warn`，不阻断）。这直接违反 `README` 的核心约束"each item must fit one image"。

**建议**：截断发生时（a）升级为 error 并触发重写/缩短；（b）在 `meta.json` 里记录 `rendered_chars` vs `source_chars`，让损耗可见。

#### P1-3 三个"标题真相"不一致

| 位置 | 值 |
|---|---|
| `run.py:281` `digest_title` | `围场过去24H新闻` |
| `publisher/telegram.py:50` | `围场过去24H新闻` + `%y.%m.%d` |
| `generator/images.py:111` footer | `围场过去24H新闻` |

`README:85` 声明标题"固定为"，但 Telegram 文本实际带日期后缀，图片脚注又不带。三处独立硬编码，改一处不会同步。

#### P1-4 投递只发标题，正文留在地面

```python
# publisher/telegram.py:53-59
def _format_digest_text(draft, max_chars=..., title=None):
    text = title or str(draft.get("title") or "")
    return _trim_text(text, min(max_chars, TELEGRAM_MESSAGE_LIMIT))
```

`max_text_chars: 1000` 配置了却从未用上——`text` 永远是标题。正文只存在于 PNG 像素和 `preview.html` 的复制按钮里。对一个"每日草稿送审"的流程，审核者必须回到电脑打开 HTML 才能拿到可复制文案，Telegram 通路的价值被削掉一半。

**建议**：把 `preview._format_items_for_copy` 的产物作为第二条消息（或 media group 的首图 caption）发出去。

#### P1-5 `/output` 无保留策略

实测 `output/` 已 **81 MB**，其中 `output/2026-07-15` 单个 43 MB。`story_db` 有 30 天保留，但**输出目录没有任何清理**。VPS 上按每天 ~1 MB + 手动重跑，一年会累积到数百 MB 且只增不减。

#### P1-6 发布失败仍记为"已发布"

`run.py:433-441`：Telegram 抛异常 → `enqueue_pending_delivery` → `raise`。异常冒泡到 **同一个** `try`，被 `except` 捕获后 `return 1`。所以历史不会写——**这点是正确的**。

但反向情形有洞：`push_digest_to_telegram` 内部先 `sendMessage` 再 `sendMediaGroup`。若文字已发出、图片失败，异常抛出 → 队列记录 → 下次"补偿"会**重发标题**。接收方看到重复标题。缺一个投递幂等键。

## 4. 做得好的地方（不要重写）

## 7. 同类项目横向对比（GitHub 调研）

调研方式：约 20 次 GitHub 代码搜索（中英双语）、约 30 次仓库元数据拉取、逐份阅读 README / SKILL.md / issue。星标数为 2026-09-11 通过 GitHub API 实读。

### 7.0 一个重要结论先说

**当前"Telegram 推给本人、由本人手动发小红书"的架构，是唯一合规的选择——它不是待修复的缺陷，而是正确的设计。**

小红书在 **2026-07-17** 发布了针对 AI 托管账号的治理公告，明确禁止：

> 「使用 AI 工具或第三方平台自动生成笔记内容并自动在小红书进行发布」
> 「手机脚本、按键精灵、自动化APP……实现自动发布、自动浏览、自动点赞、自动评论、自动私信」

并声明近期处置了 **42 万个** AI 托管违规账号。

生态内 issue tracker 的实证（[xiaohongshu-mcp](https://github.com/xpzouying/xiaohongshu-mcp) ⭐15,733）：

- [Issue #668](https://github.com/xpzouying/xiaohongshu-mcp/issues/668)：开启自动回复评论后**1 天封号**
- [Issue #777](https://github.com/xpzouying/xiaohongshu-mcp/issues/777)：**仅取消一次收藏 + 读取一次帖子**即被警告（注意这是"读"不是"发"）
- 该项目 README 主动推荐浏览器扩展版 [`x-mcp`](https://github.com/xpzouying/x-mcp)，理由是"无服务器 IP 风险"——等于承认机房 IP 自动化本身就是检测信号

**给本项目的建议**：

1. **保持手动发布**，不要接自动发布；
2. 若要自动化，只自动化"读/分析"，且保持低频、拟人节奏；
3. 借鉴 [estelledc/xiaohongshu-publish](https://github.com/estelledc/xiaohongshu-publish)（⭐0）的 **"发布胶囊"** 思路——把标题、正文、图片顺序、原生话题、AI 声明打成一个结构化、可直接复制的交付物发给本人。**这恰好补上 P1-4（Telegram 只发标题）**，且完全不碰账号；
4. 注意平台正在推进 **AI 生成内容需声明**，即使手动发布也可能需要标注。

### 7.1 最值得借鉴的 6 项技术（按性价比排序）

#### T1 用 HTML/CSS + Playwright 渲染卡片，替掉手写 Pillow 排版 ⭐ 最高性价比

两个项目独立得出同一结论：

- [SOUMILCHANDRA/Pitwall-Media](https://github.com/SOUMILCHANDRA/Pitwall-Media)（⭐1）：Jinja2 模板 → Playwright 截图，CLI `--event --session`
- [op7418/guizang-social-card-skill](https://github.com/op7418/guizang-social-card-skill)（⭐6,974）：明确要求"用 Playwright 或浏览器截图工具导出每个 `.poster` 节点"，画布 `1080×1440`（正是本项目尺寸）

**为什么对本项目特别值**：当前**同时维护两套排版实现**——`generator/images.py` 的 Pillow 手算字宽换行，和 `preview.html` 的浏览器渲染。两者会不一致（`_wrap_text` 的宽度启发式 vs 浏览器真实断行）。改成模板后 CJK 断行、字体栈、flex/grid 全部交给浏览器，`images.py` 里 100 多行字宽算术与 P1-2 的截断问题一起消失。

浏览器方案太重的话，[vercel/satori](https://github.com/vercel/satori)（⭐13,931）可无头渲染 HTML+CSS→SVG，但 CSS 支持较弱且 CJK 字体要自理。

#### T2 把候选排序的**打分拆解**持久化并在预览页展示

[wildlifechorus/condenseit](https://github.com/wildlifechorus/condenseit)（⭐82）把约 13 个信号通道的加权贡献逐项展开，每张卡片带一个可折叠的 **"Why ranked here?"**。

**为什么对本项目特别值**：`AGENTS.md` 自己已经写了"重复手动运行可能因冷却机制被压制"——这是一个**已知的调试痛点**。`shortlist_reasons` 现在虽然算了，但只存进 `PostItem.extra`，没有集中落盘、没有在 `preview.html` 里露出。把贡献项（`tier: +3.0 / article_bonus: +1.5 / cross_source: +2.0 / social_cap: -0.5 / decay: ×0.82`）写进 SQLite 并渲染到预览页，就能把"为什么今天没这条"从谜案变成一次查询。

附带值得抄的：来源优先级 + 每源的包含/隐藏/高亮关键词、**预算页（每日/每月限额）**、API key 静态加密。

#### T3 断点续跑（checkpointing）

[chengjialu8888/AI_News_Digest](https://github.com/chengjialu8888/AI_News_Digest)（⭐19）用 `.progress` / `.done` 标记文件 + 阶段化执行，失败从最后一个有效阶段恢复；理由是 60+ 源会导致上下文爆炸。

**为什么对本项目特别值**：`run.py` 一次运行要调多次 DeepSeek，目前**任何一次 429 或容器重启都会丢掉当天全部工作**。这是清单上最便宜的可靠性改进：加一个 `run_state/` 目录和 `--resume`，每个阶段落一个 marker。

同一个项目的另一个可借鉴点：**门控返回 `Report[value, status, evidence]`，失败短路，证据累积成 QA trace 并打印在摘要里**——这正是把 `evidence_gate → fact_check → final_review → quality_guard` 这条链的"为什么被丢"结构化输出的做法，直接回应本文 P1-1 和 D4。

#### T4 生成器与评审器**通过文件**而非对话分离

[greeun/ai-news-digest-harness](https://github.com/greeun/ai-news-digest-harness)（⭐1）的原则："agents never see each other's reasoning. They communicate exclusively through files"，产物 `spec.md → generator_report.md → critique.md`（PASS/FAIL + 证据），FAIL 时用**全新** generator 重试最多 3 轮。

**对照本项目**：`digest_writer.py` 目前确实是"草稿 → 事实核查 → 终审"的独立调用，方向上已经对了。缺的是 (a) `critique.json` 这种结构化 PASS/FAIL 交接物，(b) **带 critique 的重试**——现在门禁失败直接抛异常，没有"把问题反馈给模型重写一次"的机会。这正好是 P1-1 的正解。

#### T5 用采样自洽性做正交的幻觉门控

[potsawee/selfcheckgpt](https://github.com/potsawee/selfcheckgpt)（⭐629）：同一 prompt 采样 N 次，按句统计自洽性，**零外部资源**检测幻觉。

**为什么对本项目特别值**：当前只有**一次**事实核查调用。单次调用抓不到"模型自信地给出错误裁决"这一失效模式。把核查 prompt 跑 3 次（温度调高），任何裁决翻转的断言打标。成本：每个 digest 多 2 次 DeepSeek 调用，在本项目量级上可忽略。

#### T6 接入结构化官方 F1 数据作为事实锚点

- [theOehrly/Fast-F1](https://github.com/theOehrly/Fast-F1)（⭐5,356）：计时/遥测/赛果
- [jolpica/jolpica-f1](https://github.com/jolpica/jolpica-f1)（⭐899）：免费 Ergast 兼容 API，`http://api.jolpi.ca/ergast/f1/`
- [br-g/openf1](https://github.com/br-g/openf1)（⭐1,726）：含**车队无线电**
- [f1db/f1db](https://github.com/f1db/f1db)（⭐614）：提供 SQLite 发行版，可打进镜像做离线查询
- [harningle/fia-doc](https://github.com/harningle/fia-doc)（⭐56）：解析 **FIA 官方 PDF**（参赛名单、轮胎配方、排位/正赛成绩）

**为什么对本项目特别值**：本管线**纯文本驱动，从不查任何官方数据源**，所以"积分榜/赛果/罚单"这类数字**在构造上就是不可验证的**——而这正是 LLM 最容易写错的一类事实。现状是靠 `config.yaml` 里一份 2026 赛季快照撑着（见 P2-6 与 D12）。

建议：把 `analyzer/standings.py` 那套脆弱的 HTML 正则（`_extract_from_tables`，只认四大车队）换成 jolpica JSON API，并让证据门控拿官方数字校验 LLM 输出。这同时解决了 D12 的"硬编码赛季事实"问题。

### 7.3 对照结论

**本项目相对生态的差异点（差异化优势，别丢）**：确定性门控链（分层/跨源/时间衰减/社交配额/冷却/双记忆）在同类项目里是明显更成熟的。调研到的 n8n / Dify 模板（如 [n8n 6011](https://n8n.io/workflows/6011-daily-ai-news-digest-with-rss-llama-32-summarization-and-telegram-delivery/)）都是 Merge → RSS → 总结 → Telegram，**跳过全部门控**。`AGENTS.md` 里"确定性门控优先于 LLM"这条原则是对的，值得坚持。

**生态普遍有、本项目缺的 8 项**：

1. 近似/语义去重（只有 URL 与文本相似度）
2. 源健康检查（Reddit/RSS 可以在 Docker 里静默失效数天）
3. 断点续跑（一次失败丢一天）
4. 纳入/剔除决策的可解释留痕
5. 读者反馈回流（手发小红书后无任何信号回到排序）
6. 结构化官方 F1 数据（导致积分/赛果类事实不可验证）
7. LLM 输出回归测试（改 prompt 目前无护栏）
8. 成本/token 预算追踪与告警

#### R4 · P1：补偿成功后，resume 会再次投递同一份稿件

- 对照第 8.2 的续跑承诺和正文 D6/P1-6 的投递语义。上次投递失败会在 `run.py:607` 入队；下次 `--resume --push-telegram` 先在 `335-336` 补偿，成功后队列虽移除该项，run checkpoint 却仍未标记 delivered；`365` 继续选中它，并在 `603` 再次发送。
- **复现**：失败入队的运行恢复时，同一稿件的发送调用顺序为 `['queue_digest', 'resume_digest']`。这不只是原报告描述的“文字成功、图片失败后重发标题”，而是恢复流程内的整份重复投递。
- **建议验收**：补偿与续跑共用投递完成状态，补偿成功后禁止同一运行再次发送；增加“入队→补偿成功→resume”的调用次数断言。
