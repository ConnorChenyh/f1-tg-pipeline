# 开发规范

## 作用域

本规范只适用于本仓库。它是个人项目，不依赖公司工作区的开发流程、业务数据库、凭据或工作日志。入口及隔离规则见 [AGENTS.md](../AGENTS.md)；模块设计见 [架构文档](architecture.md)。

## 环境与依赖

- 以 Docker 和 CI 使用的 Python 3.11 为验证基线，不能仅凭本机较新 Python 通过就判断兼容。
- 使用仓库 `.venv`，按 `requirements.lock` 安装依赖。
- `requirements.txt` 维护直接依赖；依赖升级时同步锁文件，在干净的 Python 3.11 环境验证，避免混入全局环境的包。
- 配置项放在 `config.yaml`；凭据放在项目 `.env` 或部署环境，不输出或提交密钥。新增环境变量时更新不含真实值的 `.env.example`。

## 改动原则

- 先确认当前分支、工作区差异和相关调用链，保留与任务无关的修改。
- 修复以可复现的问题为起点，只做解决问题所需的改动，不顺手重构无关模块。
- 保持 `PostItem`、话题、草稿和运行状态的接口兼容；确需调整时同时检查消费者、历史产物读取和恢复流程。
- 网络请求有超时，重试有上限；复用现有网络、URL 安全、原子写入和锁机制。
- 缓存提取逻辑或数据结构变化时，考虑缓存失效；不能让旧缓存掩盖新行为。
- 测试使用临时目录和模拟客户端，不改真实发布历史、投递队列或生产数据库，不发送 Telegram。

## 内容与提示词

- 原文是主要证据，RSS 摘要和模型摘要不能替代正文。检查正文是否混入导航、比分、推荐视频，不能把抓取缺失说成原文未提及。
- 以报道发布时间筛选窗口；新发表的人物报道、采访和回顾可以独立成卡，同时准确表达事件先后，不将旧事件写成刚刚发生。
- 不设最低字数、目标字数或固定句数。保留重要细节、数字、引语和必要背景，避免空话、重复和无关科普。
- 核查过程及材料局限放在内部备注；正文保留新闻所需的来源归属和实际状态，如“仍待批准”，不解释写作者为何不补充。
- 修改写稿要求时同时检查写稿、事实核查、终审和确定性质量关卡，避免互相冲突。
- 不靠关闭事实关卡或清空历史绕过失败。重复运行、历史回填及投递补偿的行为应保持一致。

## 验证

代码改动按影响范围增加有意义的回归测试，覆盖故障样例和容易误伤的正常情况。发布前执行：

```bash
.venv/bin/python -m unittest discover -s tests
.venv/bin/python -m compileall -q analyzer generator collectors publisher run.py scheduler.py
git diff --check
```

纯文档修改检查链接、命令与实现的一致性以及 diff 即可。图片布局修改需要查看实际渲染结果；正文抽取修改应尽可能用已获授权的真实页面验证。线上内容导出限定在获授权的范围，临时调查文件不提交。

单元测试和 mock 路径能验证结构及规则，不能证明模型实际写作质量。明确区分离线验证、真实模型运行和生产投递；未执行的验证不能宣称通过。

## Git 与交付

- 交付前检查文档影响：功能与使用方式更新 README，开发约定更新本规范，模块职责和数据流更新架构文档，配置、部署和排障流程更新运维手册。相关文档与代码在同次改动中提交；纯内部改动且不影响已有描述时无需修改文档。

- 提交只包含任务相关文件，不提交 `.env`、`output/`、临时导出或凭据。
- 使用说明具体问题与结果的提交信息；需要新分支时默认使用 `codex/` 前缀。
- 按用户授权执行提交、推送和部署；已有明确授权不重复询问。
- 部署按 [运维手册](operations.md#vps-deployment) 执行，核对运行版本、容器状态和下一次调度。
- 手动生成和 Telegram 发布区别于部署验证。用户要求等待定时效果时，不额外手动推送。
- 完成后简要说明改动、验证及是否部署；不生成公司工作日志。
